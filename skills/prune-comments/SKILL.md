# Prune Comments

Remove every comment the code can speak for. Rewrite the survivors so they read faster than the code they guard.

## The Premise

Code is the source of truth. A comment is a second, unverified copy of it. Nothing compiles it, tests it, or fails when it goes stale. Every comment left in place bets that future edits keep it honest — and that bet loses quietly, leaving a comment that misinforms the next reader.

The risk peaks on internal API surface: IntelliSense and LSP hovers promote a stale doc comment into a tooltip read *instead of* the code. A wrong tooltip is worse than no tooltip.

Default to no comment. A comment must earn its place against the bar below. Being accurate today is not enough.

---

## Supported Scopes

`$ARGUMENTS` determines what to analyze:

- `file <path>` — one file.
- `dir <path>` — all source files under a directory.
- `changes` — the current git diff (staged + unstaged). Default.
- `branch [<base>]` — files changed between the current branch and `<base>` (defaults to `main`).
- `all` — the entire codebase under the working directory.

If `$ARGUMENTS` is empty, null, or unrecognized, use `changes`.

For `changes` and `branch`, evaluate only the comments inside changed hunks and their immediate surroundings. Do not expand into untouched regions.

---

## Step 1 — Test Every Comment

Run each comment down this ladder in order. The first rung it lands on decides it. Only a comment that falls through every rung survives.

1. **Obvious from reading the code?** → remove.
2. **Inferable from reading the code?** → remove.
3. **Mildly complex, still reasonably inferable?** → remove.
4. **Does the surrounding context answer the "why"?** — function name, type name, file, covering test, adjacent call site → remove.
5. **Complex and obscure enough that a reader fluent in the language could not reconstruct the "why"?** → keep, then rewrite per Step 3.

A comment describing *what* the code does never reaches rung 5. Only a *why* survives.

### Remove On Sight

- **Restatements.** `// increment the counter`, `# loop over users`, `// return the result`.
- **Section labels** duplicating structure: `// --- Properties ---`, `// constructor`, region wrappers used as signposts.
- **Signature echoes** — doc comments whose `@param` / `<param>` / `Args:` entries add nothing to the parameter name and type: `/// <param name="userId">The user id.</param>`.
- **Narrated steps.** `// Step 1: validate`, `// Step 2: save` above self-evident calls.
- **Commented-out code.** Delete it. Git is the archive; dead code in a comment is dead code with camouflage.
- **Changelog and authorship noise.** `// Added by X on 2024-03-01`, `// Modified for ticket 123`. Blame covers this.
- **Comments already wrong.** Remove — do not repair a stale comment into a correct restatement.
- **Doc comments on private, internal, or non-published members** that restate the member. Highest drift, highest cost: tooling surfaces them as authoritative and nothing verifies them.

### Keep, Then Tighten

A comment survives only when it carries information unrecoverable from the code:

- **Magic numbers and strings** — where the value came from, when it cannot be named instead. `// Stripe caps webhook retries at 3.`
- **Code that looks arbitrary or wrong but is not** — ordering matters, the extra call is deliberate, the redundant-looking guard prevents a real failure.
- **External constraints** — protocol requirement, vendor quirk, upstream bug worked around, regulatory rule. Cite the source when one exists.
- **Deliberate trade-offs** — why the slower or uglier path beat the obvious one.
- **Non-obvious invariants** a caller could otherwise violate.
- **Directives that only look like comments** — `// eslint-disable-next-line`, `# noqa`, `# type: ignore`, `//go:build`, `#pragma`, `// nolint`, `// @ts-expect-error`, `<auto-generated/>`. These are code. Never touch them, and never touch a comment whose position they depend on.
- **License and copyright headers.** Never touch.
- **`TODO` / `FIXME` / `HACK` carrying a tracker reference or a concrete condition.** A bare `// TODO: fix this` with no owner, ticket, or condition carries no information — remove it.
- **Doc comments on genuinely published API surface** — a package consumed outside this repository, where docs are part of the contract. Keep, held to Step 3's brevity bar.

> If the scope contains a published-package boundary and membership in that contract is ambiguous, leave those doc comments untouched and say so in the report.

---

## Step 2 — Prefer Better Code Over a Comment

A comment sometimes survives only because a name is vague, a function does too much, or a value is unnamed. The real fix is in the code: extract a named constant, rename the variable, split the function.

Do not make that edit here. This skill changes comments, not behavior. Record it under *Follow-ups* in the report and leave the comment in place.

---

## Step 3 — Rewrite the Survivors

A kept comment must read faster than the code it explains. If the reader is better off reading the code, the comment failed.

- **One line.** Two only if the constraint needs it. Never a paragraph.
- **Lead with the reason.** Cut "This is because", "Note that", "In order to", "Basically".
- **State the constraint, not the mechanism.** The mechanism is right there.
- **Name the source** when one exists — vendor, spec, ticket, bug.
- **No hedging, no history, no apology.**

Before:

    // We need to retry here because sometimes the payment provider's API
    // will return a 503 even though the request actually succeeded on their
    // side, so we check the idempotency key first before retrying, otherwise
    // we would end up double-charging the customer.

After:

    // Provider returns 503 on succeeded requests; re-check the idempotency key or we double-charge.

Collapse multi-line block comments to one line wherever the content fits. Downgrade a surviving doc comment to a plain comment only when the member is not part of a published contract and the tooltip adds nothing.

---

## Step 4 — Apply

Edit files in place under these constraints:

- **Comments only.** Do not alter one token of executable code — no renames, no reformatting, no import changes. If removing a comment would change behavior, it was a directive: restore it.
- **Leave whitespace clean.** No orphan blank line, no doubled blank line, no gap between a decorator/attribute/annotation and its declaration.
- **Preserve indentation** of every comment that stays.
- **Skip generated and vendored files** — under `node_modules/`, `vendor/`, `dist/`, `bin/`, `obj/`, plus `*.g.cs`, `*.generated.*`, or any file with an auto-generated header.
- **Source code only.** Do not touch Markdown, docs, or config files.
- If every comment in a file is load-bearing, leave the file alone and say so.

---

## Step 5 — Report

After applying, output this and nothing more:

    ## Pruned Comments — {scope}

    **Removed:** {n} across {m} files
    **Rewrote:** {n}
    **Kept:** {n}

    ### Removed
    | File:line | Comment (truncated to 60 chars) | Rung |
    | --------- | ------------------------------- | ---- |

    ### Rewrote
    | File:line | Before (truncated) | After |
    | --------- | ------------------ | ----- |

    ### Kept
    | File:line | Comment | Why it survived |
    | --------- | ------- | --------------- |

    ### Follow-ups
    - {file:line} — {the code change that would let this last comment go}

    Review with: `git diff`

- **Rung** is the Step 1 ladder number that removed the comment (1–4).
- Omit empty sections, *Follow-ups* included.
- If nothing was removed, output one line saying the scope is already clean.
- No preamble, no closing summary, no next steps beyond the `git diff` line.
