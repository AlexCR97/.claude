# Azure DevOps

`fetch` goes through `az rest` only: `az` holds the credentials, and nothing here reads, prints or stores a token. Coordinates are `organization` (namespace level) and `project` (product level). No organization or project default exists: an unbound organization is an error that points at `/sdlc:setup`.

- **An id names no project.** On first intake `fetch` reads `System.TeamProject` from an organization-level URL (no project in it), then files the work item under the product bound to `{organization, project}`. The organization comes from `--coordinate organization=...`, the session context's namespace, or the one organization bound anywhere. A team project bound to no product is an error naming `{organization, project}` and pointing at `/sdlc:setup`, with nothing written: nothing moves a ticket once filed, so it is never parked under a `default` product. A refresh reads the ticket's own recorded coordinates and does not ask again.
- **Mirror shape.** `raw/raw.json` holds `meta`, `work_item` (the `$expand=all` response: fields, `rev`, relations), `comments`, `relations` and `attachments`. Prose fields and comments are HTML. `relations` groups `parent` (or null), `children`, `predecessors`, `successors`, `related`, `hyperlinks` and `other` (artifact links such as pull requests, kept as returned). Each related work item carries `id`, `title`, `state`, `type`, one level only; one the account cannot read has those empty. Comments are read page by page (`continuationToken`).
- **Revision.** `ticket.json` `fingerprint` is `{"rev": N}`, the work item's `rev`. A cheap probe is `GET .../_apis/wit/workItems/{id}?fields=System.Rev`.
- **Drift check.** `fetch <ref> --check` is the read-only drift check: it writes nothing and prints `{ref, ticket_dir, changed, status, reason?, recorded, live, coordinates, last_fetched_at}`. `status` is `unchanged`, `changed`, `never_mirrored` (no recorded fingerprint; `changed` is true, as nothing vouches for the mirror) or `local` (no upstream; `changed` is false). Here `live` is `{"rev": N}` from the one probe above, an organization-level request that needs no project, compared with the recorded `rev`; a different `rev` means changed.
- **Failures.** A rejected sign-in (`AADSTS`, `az login`, `Unauthorized`) or any failed request except an attachment aborts and writes nothing; a missing work item exits 5. Query parameters travel as `--url-parameters`, never in `--url`: `&` splits under the `cmd.exe` that runs the `az` shim on Windows. Responses go through `--output-file`, so non-ASCII text is not mangled by the console codepage.
- **Attachments.** Every reference is recorded with its URL, the name its author gave it and where it was found: `AttachedFile` relations, and pasted images embedded in any field or comment (these are not relations). One attachment id is one record. Download is `az rest --method get --url <attachment url without query> --output-file <file>`, with no token handled here; a failure is listed in the report with its error and never aborts. This was exercised against a stubbed `az` only; no real organization was read. A file is saved as `{attachment id}{original extension}` (ADO names every paste `image.png`); one already in `raw/` is the same attachment and is kept on refresh. A zip is kept as is, not extracted.

## Writing back (for `submit`)

Verified against Microsoft's documentation (2026-11):

- **Revision guard.** Send a JSON Patch (`Content-Type: application/json-patch+json`, `PATCH https://dev.azure.com/{organization}/{project}/_apis/wit/workitems/{id}?api-version=7.1`) whose first operation is `{"op": "test", "path": "/rev", "value": N}`, `N` being the mirror's `fingerprint.rev`. Microsoft's update examples all open this way (https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/update?view=azure-devops-rest-7.1); an edit made since the snapshot makes the test fail, so the whole patch is rejected. The page does not spell out the rejection's status code: check it when first used.
- **Link type names.** Predecessor is `System.LinkTypes.Dependency-Reverse`, successor is `System.LinkTypes.Dependency-Forward`; parent is `System.LinkTypes.Hierarchy-Reverse`, child `System.LinkTypes.Hierarchy-Forward`; related `System.LinkTypes.Related`. Source: the `az boards work-item relation list-type` output on https://learn.microsoft.com/en-us/azure/devops/boards/queries/link-type-reference?view=azure-devops (Successor -> Dependency-Forward, Predecessor -> Dependency-Reverse, Child -> Hierarchy-Forward, Parent -> Hierarchy-Reverse). Direction: the relation on a work item names what the other end is to it, so a relation `Dependency-Reverse` on item A points at A's predecessor.
- **Tags** are one `;`-separated string in `System.Tags`: read, modify, write the whole value.
