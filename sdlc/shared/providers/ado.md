# Azure DevOps

`fetch` goes through `az rest` only: `az` holds the credentials, and nothing here reads, prints or stores a token. Coordinates are `organization` (namespace level) and `project` (product level). No organization or project default exists: an unbound organization is an error that points at `/sdlc:setup`.

- **An id names no project.** On first intake `fetch` reads `System.TeamProject` from an organization-level URL (no project in it), then files the work item under the product bound to `{organization, project}`. The organization comes from `--coordinate organization=...`, the session context's namespace, or the one organization bound anywhere. A team project bound to no product is an error naming `{organization, project}` and pointing at `/sdlc:setup`, with nothing written: nothing moves a ticket once filed, so it is never parked under a `default` product. A refresh reads the ticket's own recorded coordinates and does not ask again.
- **Mirror shape.** `raw/raw.json` holds `meta`, `work_item` (the `$expand=all` response: fields, `rev`, relations), `comments`, `relations` and `attachments`. Prose fields are HTML, and so is a comment's `text`, except one posted with `format=markdown`, as a journal entry is. A comment that is a journal entry is also mirrored into `journal/` ([`journal.md`](../journal.md)); its `text` starts with the marker, as seen on a live organization (2026-11). `relations` groups `parent` (or null), `children`, `predecessors`, `successors`, `related`, `hyperlinks` and `other` (artifact links such as pull requests, kept as returned). Each related work item carries `id`, `title`, `state`, `type`, one level only; one the account cannot read has those empty. Comments are read page by page (`continuationToken`).
- **Revision.** `ticket.json` `fingerprint` is `{"rev": N}`, the work item's `rev`. A cheap probe is `GET .../_apis/wit/workItems/{id}?fields=System.Rev`.
- **Revision check.** `fetch <ref> --check` is the read-only revision check: it writes nothing and prints `{ref, ticket_dir, changed, status, reason?, recorded, live, coordinates, last_fetched_at, journal}` (`journal` and the journal statuses as [`journal.md`](../journal.md) "Mirrored entry" says). `status` is `unchanged`, `journal_only`, `journal_unmirrored`, `changed`, `never_mirrored` (no recorded fingerprint; `changed` is true, as nothing vouches for the mirror), `stale_mirror` (a fingerprint but no `raw/raw.json`: the mirror predates this shape, so `changed` is true and `reason` says to refresh with `/sdlc:intake <ref>`; upstream is not asked) or `local` (no upstream; `changed` is false). Here `live` is `{"rev": N}` from the one probe above, an organization-level request that needs no project, compared with the recorded `rev`; a different `rev` means changed. Only then does it read the work item (`$expand=all`) and its comments, downloading nothing, to tell `changed` from the journal statuses: fields, relations (type and URL) and comments other than journal entries are compared with the mirror's, leaving out the fields every revision moves (`System.Rev`, `System.ChangedDate`, `System.ChangedBy`, `System.AuthorizedDate`, `System.AuthorizedAs`, `System.RevisedDate`, `System.Watermark`, `System.PersonId`, `System.CommentCount`, `System.History`). A field missing from that list makes a post read as more than the journal: a needless refresh, never a missed change.
- **Failures.** A rejected sign-in (`AADSTS`, `az login`, `Unauthorized`) or any failed request except an attachment aborts and writes nothing; a missing work item exits 5. A call that gets no answer within 120 seconds (`SDLC_CLI_TIMEOUT` overrides) is the same kind of failure, with a hint; for an attachment it is listed in the report. Query parameters travel as `--url-parameters`, never in `--url`: `&` splits under the `cmd.exe` that runs the `az` shim on Windows. Responses go through `--output-file`, so non-ASCII text is not mangled by the console codepage.
- **Attachments.** Every reference is recorded with its URL, the name its author gave it and where it was found: `AttachedFile` relations, and pasted images embedded in any field or comment (these are not relations). One attachment id is one record. Only a URL on the ticket's own organization (`https://dev.azure.com/{organization}/...` or `https://{organization}.visualstudio.com/...`, host compared exactly) is downloaded: `az rest --resource` attaches a bearer token to whatever URL it is given, and the URLs come from text anyone with access can write. Any other URL (another host, `http`, another organization, a look-alike or userinfo host) is still recorded, with `local_filename` null and an `error` saying why, is listed under `failed` in the report, and is never passed to `az`. Download is `az rest --method get --url <attachment url without query> --output-file <file>`, with no token handled here; a failure is listed in the report with its error and never aborts. This was exercised against a stubbed `az` only; no real organization was read. A file is saved as `{attachment id}{original extension}` (ADO names every paste `image.png`); one already in `raw/` is the same attachment and is kept on refresh. A zip is kept as is, not extracted.

## Posting a journal entry (for `checkpoint`)

One comment per entry, in the posted form of [`journal.md`](../journal.md), posted as Markdown. Verified against Microsoft's documentation (<https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/comments/add-work-item-comment?view=azure-devops-rest-7.1>, 2026-11) and exercised against a live organization (2026-11): the post, the revision check reading it as `journal_only`, and a fresh home mirroring it byte for byte.

- **Post.** Write `{"text": "<posted form>"}` with a JSON encoder, UTF-8, to a scratch file outside the ticket directory, then `az rest --resource 499b84ac-1321-427f-aa17-267ca6975798 --method post --url "https://dev.azure.com/{organization}/{project}/_apis/wit/workItems/{id}/comments" --url-parameters format=markdown api-version=7.1-preview.4 --headers Content-Type=application/json --body @{scratch file} --output-file {scratch response}`, with the coordinates from `ticket.json` and the project percent-encoded. `format` is required and is `markdown` or `html`; with `markdown` the marker comes back as the first line of `text` (with `renderedText` the HTML). Exit 0 and a comment id in the response (`id`, which Microsoft's sample names `commentId`) mean it landed.
- **Already posted?** `GET` the same URL with `api-version=7.1-preview.4`, page by page (`continuationToken`), as `fetch` reads comments; a marker as the first line of a comment's `text` is an entry already upstream.
- A post changes the work item's `rev`.

## Writing back (for `submit`)

The revision guard and link type names are verified against Microsoft's documentation (2026-11); the create and edit notes after them come from the previous suite's recipes and were exercised against a stubbed `az` only, never a real organization:

- **Revision guard.** Send a JSON Patch (`Content-Type: application/json-patch+json`, `PATCH https://dev.azure.com/{organization}/{project}/_apis/wit/workitems/{id}?api-version=7.1`) whose first operation is `{"op": "test", "path": "/rev", "value": N}`, `N` being the `live` revision of the check `submit` runs just before the write: the mirror's `fingerprint.rev` when it is `unchanged`, the revision journal posts moved it to otherwise. Microsoft's update examples all open this way (<https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/update?view=azure-devops-rest-7.1>); an edit made since the mirror was taken makes the test fail, so the whole patch is rejected. The page does not spell out the rejection's status code: check it when first used.
- **Link type names.** Predecessor is `System.LinkTypes.Dependency-Reverse`, successor is `System.LinkTypes.Dependency-Forward`; parent is `System.LinkTypes.Hierarchy-Reverse`, child `System.LinkTypes.Hierarchy-Forward`; related `System.LinkTypes.Related`. Source: the `az boards work-item relation list-type` output on <https://learn.microsoft.com/en-us/azure/devops/boards/queries/link-type-reference?view=azure-devops> (Successor -> Dependency-Forward, Predecessor -> Dependency-Reverse, Child -> Hierarchy-Forward, Parent -> Hierarchy-Reverse). Direction: the relation on a work item names what the other end is to it, so a relation `Dependency-Reverse` on item A points at A's predecessor.
- **Tags** are one `;`-separated string in `System.Tags`: read, modify, write the whole value. Read the live value (the mirror's `System.Tags` may be out of date), compare case-insensitively, keep entries in their order and casing, join with `;`. An empty result is `{"op": "remove", "path": "/fields/System.Tags"}`, not an empty string.
- **Prose is HTML.** `System.Description`, `Microsoft.VSTS.Common.AcceptanceCriteria` and `Microsoft.VSTS.TCM.ReproSteps` (a Bug's body usually lives there) are HTML fragments: convert Markdown (paragraphs, lists, headings, code, links, emphasis; escape `&`, `<`, `>`) and show the converted HTML in the preview. A `- [ ]` criterion becomes a plain list item: Azure DevOps has no checkboxes.
- **Create.** `POST https://dev.azure.com/{organization}/{project}/_apis/wit/workitems/${type}` (`$` is literal, so quote the URL; a type with a space is percent-encoded, `User%20Story`), `api-version=7.1`, `Content-Type=application/json-patch+json`, one `add` per field in the body, through `az rest --resource 499b84ac-1321-427f-aa17-267ca6975798` like every read. The response carries the new `id`; fetch it back with `--coordinate organization=...`. The native type is read from the project (`GET .../{project}/_apis/wit/workitemtypes`), since process templates name them differently: user-story is the first of User Story, Product Backlog Item, Requirement, Feature the project has; bug is Bug or Defect; task, spike and tech-debt are Task or Issue. No tag marks a spike or tech-debt: the type is recorded locally. None found: list the project's types and ask.
- **Edit.** One JSON Patch per change, every field in it, opening with `test /rev`; it lands whole or not at all. `State` is `System.State`, one the type allows (others are refused). Never use `az boards work-item update` for an edit: it has no revision guard.
- **Rejection.** A failed `test /rev` rejects the whole patch: report it as given and stop; never retry with the revision changed. Its exact status code and wording were not verified against a live organization.

## Pull requests (for `pr`)

For a repository whose remote is on Azure Repos, whatever the ticket's source. The organization, project and repository come from the remote: `https://dev.azure.com/{organization}/{project}/_git/{repository}` (also with `{organization}@` before the host), `https://{organization}.visualstudio.com/{project}/_git/{repository}`, or `git@ssh.dev.azure.com:v3/{organization}/{project}/{repository}`. Percent-decode them from the URL, percent-encode them in a request. From Microsoft's REST and `az repos` documentation; not exercised against a live organization.

- **Find.** `az repos pr list --organization https://dev.azure.com/{organization} --project {project} --repository {repository} --source-branch {branch} --status active`. A draft is `active` with `isDraft` true.
- **Create** through `az rest`, so the Markdown description survives the shell: write `{"sourceRefName": "refs/heads/{branch}", "targetRefName": "refs/heads/{target}", "title": ..., "description": ..., "isDraft": true}` with a JSON encoder to a scratch file, adding `"workItemRefs": [{"id": "{id}"}]` when the ticket is a work item of the same organization, then `az rest --resource 499b84ac-1321-427f-aa17-267ca6975798 --method post --url "https://dev.azure.com/{organization}/{project}/_apis/git/repositories/{repository}/pullrequests" --url-parameters api-version=7.1 --headers Content-Type=application/json --body @{scratch file} --output-file {scratch response}`. The response's `pullRequestId` is the number; its page is `https://dev.azure.com/{organization}/{project}/_git/{repository}/pullrequest/{pullRequestId}`.
- **Update.** The same call with `--method patch` on `.../pullrequests/{pullRequestId}` and `{"title": ..., "description": ...}`.
- **Ready.** `az repos pr update --id {pullRequestId} --organization https://dev.azure.com/{organization} --draft false`.
- **Status.** `az repos pr show --id {pullRequestId} --organization ...`: `isDraft` is `draft`, else `status` `active` is `open`, `completed` is `merged`, `abandoned` is `closed`; a reviewer's `vote` of `10` or `5` is `approved`, `-5` `waiting for author`, `-10` `rejected`.
- **A description is capped at 4,000 characters.** Over it, shorten Changes and say in the body that it was shortened.
- `#{id}` in a description mentions a work item of the same organization.
