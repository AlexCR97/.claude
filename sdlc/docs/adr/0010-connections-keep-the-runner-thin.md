# Connections keep the runner thin

A connection is a credential profile the model never reads, and a `connection` verb that does only what must come out identical every run: resolve the profile, inject its variables into a command's environment, mask them in the output, and refuse a production profile or a `sensitive` target until the user approves. How to consume the system (which tool, which endpoint, how to page) is the model's, guided by instructions read on demand per kind. This extends [ADR 0006](./0006-scripts-and-instructions-are-for-mechanical-work-only.md) from tickets to credentials. It also extends [ADR 0008](./0008-a-ship-run-may-commit-push-and-open-pull-requests.md): a ship run's hard stops now include writing through a connection and reaching a production connection. A ship run uses a connection only when its invocation or the ticket names it, runs a read-only call on a non-production connection unattended, and never probes after a deployment on its own.

We rejected a built-in client per kind, such as a REST client that can only send GET: it would limit the model to what its author foresaw and need upkeep for every tool, the reason ADR 0006 gives for scripts in general. We rejected making an MCP server the default, because it puts the secret in configuration the agent's own process inherits and cannot hold the production gate; the developer may still choose one for a system that has no better way in. The cost is that the runner cannot tell whether an arbitrary command writes, so read-only is guidance and not enforcement. We offset it three ways: a production profile should hold read-only credentials, output masking catches a value printed whole (4 or more characters, so a transformed value or a short one is not caught), and `/sdlc:connect` prints permission entries for the developer to add to their own `settings.json`. A value the child shell expands also shows in this machine's process list while the tool runs, though never in the model's context.
